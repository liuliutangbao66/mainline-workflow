# Project Flow 0.1.0

试用版，2026-09-26。每个项目固定本版工具与协议；发布后修改另发新版本，既有任务不追溯升级。

## 最小循环

用户决定目标与重要取舍。一个主线维护者准备阶段任务，执行者在授权内调查/实施/自验，主线按证据接受或返工。需要独立判断才另设验证者。简单工作可不建立流程。

任务状态：ready → running → pending_review → accepted。pending_review可返工到新一轮ready。中途可blocked并恢复原状态，也可cancelled；不自动恢复、不自动重试业务操作。

ready已有报告时不再开始执行。主线核查归属、版本和停止状态后，可用带existing_delivery_checked说明的submit直接登记为待验收；不会自动接受。

主线承担生命周期写入；执行者只写当前任务允许的成果和当轮交付。角色标签及文件锁是协作约定，不提供认证、沙箱或强制操作系统权限。

## 文件

- state.json：权威登记；STATE.md：派生摘要。当前任务只指向契约，不重复完整授权。
- PROJECT.md：本版项目目标和约束。需要变更项目约束时先协调、保留旧契约，不绕过校验手改。
- tasks/Txxx/task.json及其派生task.md：冻结的阶段契约，目标、输入、范围、验收、执行者、停止条件、协议。
- attempt-NN/report.md与原始证据：执行者交付。submission.json冻结明确候选和证据；review.json保存主线决定与验证依据。
- history：必要的判断/交接/恢复记录，接手不默认全部读取。返工保留旧轮。

初始化保留已有AGENTS不变；是否接入现有入口由使用者决定。协议和工具在项目内固定，不自动升级全局配置。

## 验收

报告出现只意味着发现交付。提交后仍待验收；接受须逐项核对约定条件与证据。需独立验证时实施者不能自称独立验证者。成果或证据变更后旧结论不覆盖当前版本；选择目录可检测其中新增、删除和修改文件。

历史接受不会因后续合理改版被删除，但当前状态检查应披露版本不匹配。文件哈希是内容标识，不是备份；成果恢复仍依项目的Git/归档机制。测试日志由实际执行产生，工具不能认证其真实性。

旧轮证据不再匹配时保留可追溯警示，不阻塞已重新核查的新一轮；当前轮仍严格拒绝变化的证据。冻结的提交/审查记录自身被改动始终报错。brief同时显示当前文件匹配情况，不能只依据历史accepted文字接续。

## 收尾

交付审查、重要授权/阻塞变化和交接触发收尾：保存关键依据，替换当前判断与下一条件，check检查一致性，最终回复说明结果与限制。普通答疑不触发。不向状态追加流水账，不强制每轮写学习日志。

## 接手

先看brief/STATE、PROJECT及当前任务，仅按需读历史。阶段结束可换会话；中途必须带现场恢复信息。processes/budget/worktree可写未知，接手在真实环境核对再继续；禁止把旧文字当实时状态。指导权交接须已有授权，不假设同时存在的会话能自动收到通知。

## 工具边界

工具不启动模型、业务命令、比赛、部署或服务；不发消息、不消费预算、不管理Git、不强制执行文件范围。它只能检查命令经手的状态、声明的范围和选定文件。

跨OS采用相对路径，业务环境仍需操作者确认。锁冲突默认拒绝，先核对主机和进程；不能因等待时间长自动删锁或抢指导权。状态文件是本地单机协作记录，不支持跨主机并发写、云同步冲突合并或恶意用户隔离。
