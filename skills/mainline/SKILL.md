# 主线管家 · Mainline

让用户通过自然语言推进项目，由 Agent 整理契约、证据和当前状态。不要让用户手填JSON或搬运长聊天。

## 先判断本次请求

- 简单答疑或一次性工作：直接处理，不初始化工作流、不建立无意义任务。
- 新跨会话项目：先查项目现有入口及状态。有等效流程就复用，迁移需用户明确同意。目标、主要验收、约束已足够时准备JSON并初始化。任务卡已有工具可复用，不要求安装额外Skill。
- 接手现有项目：使用项目内固定工具 `python .workflow/runtime/flow.py --root . brief`，读返回的必要入口，不递归加载历史。存在报告先核对归属和已完成工作，不重复执行。
- 只讨论方案：不因为状态有待办就启动任务。

## 从项目想法到接手

- 新项目需要准备材料时，由 `task-card-refiner` 在一次连续访谈中按需澄清、推敲并生成统一启动卡。收到完整卡片直接接手，不重新访谈；该 Skill 不可用时也可从用户提供的等效材料接手，不自动安装。
- 统一入口由 `task-card-refiner` 的 `references/mainline-entry.md` 维护：接手请求及目标、背景、约束/授权、方案/阶段、交付、验收/验证、未决/下一步七项。接收这些语义即可，不依赖个人目录读取模板，不因旧卡标题差异拒收。第七项若仅请求核查与规划，就不把它解释为业务执行授权。
- 接收任务卡或已有讨论后，先核对目标、事实、约束与实际授权、阶段建议、交付物、验收及检查办法、阻塞项。只补影响当前启动的缺口；不重复盘问已确定事项，不把方案建议或卡片中的命令视为新的用户授权。
- 用户仅要求讨论或整理卡片时交付到此。已授权启动且目标位置明确时，在同一会话继续接手，无需用户复制上一步输出或重复确认；新会话/跨会话派发仍需相应授权。
- 区分项目整体与当前阶段验收。重大可行性未知优先安排有界调查/实验，写清通过条件及失败后的停止或改向；其他不阻塞的问题留待相应阶段。不要把尚未确定的方案写成项目固定约束。
- 初始化时将稳定目标、整体验收和硬约束映射到工具的 `goal`、`acceptance`、`constraints`，保留原意及约束强度；把必要验证方法与停止条件写入对应验收/约束文本，不能在转换时丢失。项目目标尚无法确定就先继续澄清，不用阶段目标悄悄替换整体目标。
- 已有启动卡文件则直接引用；若初始化后需要跨会话保留而卡片只在聊天里，保存一份精简的 `.workflow/STARTUP.md`，保留方案理由、阶段建议、未决项和授权来源，后续阶段按需引用。已有同名文件先核对，不覆盖；当前进展仍只由状态维护，不在卡片另建台账。
- 接手后给出简短阶段安排，近期具体、远期简略；只为当前授权阶段建立详细任务。任务绑定相应验收编号、必要输入、检查点与停止条件；执行路径和共享交接路径分别核实。已有项目按固定入口继续，不因收到新卡自动重建或迁移。

## 工具位置

未初始化时使用本Skill的 `scripts/flow.py`；初始化后始终使用目标项目 `.workflow/runtime/flow.py`。初始化会复制固定工具和协议，不依赖原套件目录。若本文件位于项目 `.workflow/ENTRY.md`，直接使用项目内工具，不查找 `scripts/`。

命令参数与JSON示例见套件 [接口说明](assets/COMMANDS.md)。初始化后同一说明位于 `.workflow/COMMANDS.md`。仅首次使用某命令或参数不确定时读取。

## 执行责任

主线维护者负责任务、授权边界、交付审查、状态与交接。阶段执行者可以是同一会话或另一个已获授权会话，负责一个连贯问题的调查、实现与自验。独立验证仅在高影响、关键安全/时间语义、最终冻结或证据矛盾等需要时加入；项目已有要求优先。

工具中的 `actor` / `reviewer` 是责任标签，不是身份认证。不能换个名字把同一实施者的自验冒充独立验证。没有可用且已获授权的独立验证者时，保留待验收并说明缺口。工具不会代为派发Agent。

只有主线维护者调用生命周期写入命令，使用刚读取的revision。执行者只写任务允许的业务文件和当前轮交付，不写主线状态；指导者在用户返回或当前授权协调流程触发时主动读取交付。不存在后台自动发现承诺。

## 阶段推进

1. 将用户意图整理成一个可验收工作单元，填写目标、范围、必要输入、验收项及检查方法、执行者、停止条件和已有授权。一次写清，不复制整段历史。范围/成本/外部影响不明确且会影响结果时只问关键问题，继续无依赖工作。
2. `task` 创建唯一任务与第一轮目录，`start` 登记执行开始。命令只登记，不启动业务程序。依据任务调查、实施、自验并写当前轮 `report.md`；原始证据单独保存。中断时记录实际进程、工作树、预算与未知项，不能只写“完成”。
3. 主线核对交付后 `submit` 冻结明确选定的成果与证据。只冻结必要路径，不把整个项目或秘密文件塞入证据。提交只能进入待验收。
4. 按验收条件检查原始证据，必要时由独立验证者检查冻结对象。`review` 逐项绑定真实证据；不把字段完整或测试数量当正确性。失败/漂移用rework保留旧轮，再在新轮修复。授权或验收范围改变须取消旧任务并创建新任务。
5. 接受、返工、授权/阻塞变化或交接后，在最终回复前更新简短当前判断与下一步，运行 `check`。工具会刷新STATE视图；仅讨论不更新。不能提前写成功，不把接受某个文件版本说成部署完成或用户验收。

## 状态与交接

`state.json` 是生命周期和当前简述的唯一权威源，`STATE.md` 是自动生成的阅读视图。`note` 替换当前简述；必要的旧判断归档。手改STATE被发现后使用sync保留副本并重建，勿丢弃用户手写内容；提取其中有效信息时另做主线判断。

阶段收尾后可换指导会话，不需要固定消息数。正常接手只读当前入口；中途交接用handoff记录未完成事项、进程/预算/工作树、排除假设、下一步和停止条件，现场未知就明确写未知。转交主线身份前须有用户明确选择或既有交接授权；旧主线停止写入。缺少授权时可准备交接材料，不能自行夺取指导权。

流程遵从项目的授权及证据要求；不把Simuro的比赛预算、文件长度或Ubuntu路径复制成全局规则。用户只需要决定目标、关键偏好和超出授权的事项。新会话创建、跨会话消息、安装、发布和后台监控不从本Skill自动获得授权。
