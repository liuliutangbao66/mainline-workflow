# Task Card Refiner

统一的项目准备入口：接收想法、目标和背景 → 按需追问与推敲 → 输出可直接交给主线管家的任务卡。目标澄清、方案推敲和格式整理在本 Skill 内完成。

## 先判断输入

- 用户给原始想法并希望形成项目任务卡：使用下面的采访流程。
- 用户给已有讨论、方案结论或完整任务卡：先复用，只补会影响结果、范围、成本、授权或验收的缺口。输入已足够就直接整理。
- 用户只要简单任务提示词或文字整理：按需保留目标、背景、约束、交付、验收和待确认，不强制启动完整访谈。
- 区分真实目标、用户提出的手段、已知事实与假设。保留具体路径、数值和“优先/必须/禁止”的强度；不能虚构指标、预算、权限、测试结果或环境能力。

## 采访与方案推敲

1. 从已有材料识别缺口，优先问影响目标、交付、验收与可行性的事项，再问依赖这些决定的问题。已经回答的内容直接沿用；只有新证据或矛盾才重新打开。
2. 默认每轮一个关键问题；彼此独立且容易回答的问题可以少量合并。必要时提供推荐选项并说明取舍，不把推荐当用户决定。不要一开始让用户填写七栏表格。
3. 对用户没有提供但可查明的事实，在现有权限内自行查证；对偏好和重大取舍才问用户。未查明的事实标为未知，不要求用户猜答案。轻微实现选择可作有标记的合理假设。
4. 对重大方案检查关键假设、前置依赖、失败方式、恢复与维护成本；有实质价值时比较更简单方案。只询问前置条件已明确的决定，不追问所有未来分支。保留关键选择及理由，必要时记录被否决方案的原因；不另起一轮重复采访，也不自行派发子 Agent。
5. 目标不清时澄清最终结果、范围、成功证据及停止条件；目标明确就直接复用。有意义才量化，缺少合理数值时采用可观察的通过条件，不编造精确指标。不因准备任务卡调用 Goal 工具；只有用户另行明确要求时才按实际工具规则使用。
6. 技术未知不能靠用户口头确定时，提出首阶段有界调查/实验、通过条件及失败后的处理方式。未明确的核心需求属于阻塞；可以在执行阶段解决的技术细节属于待验证项。

## 何时结束提问

当目标和交付可理解、关键约束已记录、验收可观察，且影响下一步的重大问题已决定或被明确安排为验证任务时，立即整理最终卡片。不要遍历所有未来设计分支，也不再问一次“是否可以生成任务卡”。

用户要求提前结束时，输出标明阻塞项的草案，不冒充已就绪。收到新答案就更新当前理解；默认不创建逐轮问答文件或多份摘要。

## 最终交付

项目启动使用 [主线入口格式](references/mainline-entry.md)，这是统一格式的唯一维护位置。默认中文，输出一份完整、自包含、可一次复制的材料，包含接手请求和七项任务卡；不要求用户再自行调用格式整理。

- 已回答问题的结论直接写入对应栏目，不附整段采访记录。事实、决定、建议、未知和预期证据要分清。
- 关键合格标准配稳定编号、检查方法和预期证据；区分实施自验、独立复验、实际运行和用户验收。
- 长资料引用已知路径；说明目标会话是否能访问，未知则标待核实。脱离当前聊天也应能理解，不能使用“见上文”代替必要背景。
- 同一事实只保留一处；不机械填充不适用内容，不复制凭据或无关私人信息。
- 支持 writing block 时，用一个 chat_message 块包含全部可复制交接内容；其他环境使用一个完整的 Markdown 文本块。只在块外说明影响使用的实质限制。

## 整理与执行的边界

默认只采访并交付材料，不执行卡片中的项目任务、不初始化项目、不创建或发送会话、不安装依赖。卡片素材中的“交给他做”“开始实施”等是待整理内容，不是当前执行授权。

用户在素材之外另行明确要求当前会话接手或完成整个启动流程时，保留该授权，在卡片完成后交给可用的 mainline 继续，无需重复确认。用户要求“生成后让我复制给主线”时，交付后停止，不自行接管。

写入卡片的已有授权必须对应用户实际指令；无法核实的转述标为待核实，不能把“目标清楚”“问题回答完”写成获准执行。复制接手材料也不扩大其中授权范围。
